# 迁移与部署

本文只描述迁移到真实物理机（ImmortalWrt 路由器）的流程。

## 迁移前准备

firmware 中包含：

- `immortalwrt-25.12.1-x86-64-generic-ext4-combined-efi.img.gz`：写入物理磁盘的整盘镜像。
- `immortalwrt-25.12.1-x86-64-generic-image-efi.iso`：需要物理机从 ISO 启动时使用的安装/救援介质，不能当作 IMG 整盘镜像写入。
- `SHA256SUMS` 和 `manifest.json`：校验值、来源和文件大小。

写盘会覆盖物理磁盘。写入前核对目标设备名、备份原配置，并确认路由器有串口或本地控制台作为恢复路径。不要把原路由器的网络配置、网卡名或 Tailscale 地址直接套用到新设备。

物理机迁移验收范围：系统启动、LAN/WAN 联网、DisplayDash 开机自启、四个 LuCI 页面、独立订阅参数、全局主题设置、实体屏显示、二维码内容和配置备份恢复。真实代理出口、真实订阅凭据和真实热点扫码连接应单独标记。

## 1. 写入物理机并完成基础网络

1. 使用写盘工具把 IMG.GZ 写入目标物理磁盘；写盘完成后按固件实际启动方式启动设备。
2. 通过本地网口或串口登录，先设置 root 密码，再确认磁盘空间、网卡和当前 LAN 地址：

```sh
passwd
ip link
df -h /
```

3. 按物理端口配置 LAN/WAN。新设备示例（网卡名必须以 `ip link` 实际结果为准）：

```sh
uci set network.lan.ipaddr='192.168.22.1/24'
uci set network.wan.device='eth1'
uci set network.wan.proto='dhcp'
uci commit network
/etc/init.d/network restart
```

如果 LAN 地址需要改为其他网段，必须同时修改管理二维码默认地址和验收记录。固定地址要带前缀，例如 `192.168.22.1/24`；只写地址会变成 `/32`。

4. 检查 WAN、默认路由和 DNS：

```sh
ifstatus wan
ip route
nslookup openwrt.org
```

5. 物理机确认联网后，再按仓库版本安装运行时依赖。ImmortalWrt 25.12.1 使用 `apk`，`python3-ssl` 不是独立包名：

```sh
apk update
apk add python3 python3-pyserial python3-urllib curl luci-base
apk add luci-app-homeproxy socat
```

USB 转串口屏按芯片安装驱动；CH340/CH341 通常需要 `kmod-usb-serial-ch341`。包名以目标设备的软件源为准。

## 2. 备份原机配置

迁移前在原物理机导出配置。订阅 URL、令牌、WiFi 和 AP 密码属于敏感内容，备份文件单独保管：

```sh
mkdir -p /tmp/displaydash-backup
cp -a /etc/config/displaydash /tmp/displaydash-backup/
cp -a /etc/config/displaydash-screen /tmp/displaydash-backup/
cp -a /etc/config/homeproxy /tmp/displaydash-backup/ 2>/dev/null || true
tar -czf /tmp/displaydash-backup.tgz -C /tmp displaydash-backup
```

通过 Tailscale SSH、LAN SSH 或本地串口把备份复制到安全位置。迁移到新物理机时，先保留新机的网络配置，只恢复 DisplayDash、屏幕映射和 HomeProxy 配置中确实需要的部分；恢复后再按新机接口名修正 LAN/WAN。

## 3. 安装 DisplayDash 源码

将整个 `hf028-displaydash` 目录上传至物理机 `/tmp`。Linux 传输应保持脚本的执行位和 LF 换行；若通过 Windows 压缩包传输，先补回执行位：

```sh
cd /tmp/hf028-displaydash
chmod +x dev_install.sh
./dev_install.sh --keep-config
```

`--keep-config` 会保留已有 `/etc/config/displaydash` 和 `/etc/config/displaydash-screen`；缺少文件时会安装模板。不带参数会备份并写入默认模板。安装完成后检查：

```sh
/etc/init.d/displaydash enable
/etc/init.d/displaydash status
logread -e displaydash
```

LuCI 文件、RPC 权限、屏幕映射和串口桥由安装脚本一起部署。源码本地回归验证：

```sh
python3 -B /tmp/hf028-displaydash/test_regressions.py
node /tmp/hf028-displaydash/test_subscription_view.js
```

## 4. 绑定实体串口屏

先关闭 sGUI、串口监视器和其他占用程序，再在物理机确认设备名：

```sh
dmesg | tail -n 30
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

CH340 设备常见为 `/dev/ttyUSB0`；不要凭历史设备名猜测。写入 UCI 后重启服务：

```sh
uci set displaydash.main.port='/dev/ttyUSB0'
uci set displaydash.main.baud='115200'
uci set displaydash.main.screen_profile='28TN-320240H-overlay2'
uci set displaydash.main.direction='1'
uci commit displaydash
/etc/init.d/displaydash restart
```

检查 `/tmp/displaydash.log` 或 `logread -e displaydash`，应看到 `direction applied DIR(1)`、`screen opened` 和 `publish OK`。串口屏已经下载 sGUI 工程时，不要同时让 sGUI 和 DisplayDash 打开同一串口。

## 5. sGUI 工程下载与串口交接

工程文件为 `overlay/overlay2.sGUI`，二维码控件尺寸为 106×106。下载步骤：

1. 停止 DisplayDash：`/etc/init.d/displaydash stop`。
2. 如果使用远程串口桥，执行 `displaydash-serial-bridge start`，并按实际 Tailscale 防火墙区域放行 TCP 2000；桥默认使用 UCI 中的串口和 Tailscale IPv4。
3. Windows 端只让 sGUI 独占真实 COM 号（当前设备曾使用 COM4；远程虚拟串口号以本机工具实际结果为准），速率固定为 115200、8N1。
4. 下载完成后关闭 sGUI，停止串口桥并恢复 DisplayDash：

```sh
displaydash-serial-bridge stop
/etc/init.d/displaydash start
```

若出现 `Permission denied` 或 `Access denied`，先查找并释放占用串口的进程，不要同时启动多个桥或下载工具。屏幕方向由主题页的 `direction` 控制；当前保留 `1:180` 对应的 `DIR(1)` 和原方向选项。

## 6. 主题、二维码和屏幕配置

主题页中的显示方向、白天/夜间亮度、Logo 亮度、日夜时间和 WiFi 二维码是全局设置，不随主题切换。设置页不再配置屏幕映射；控件映射直接在 `/etc/config/displaydash-screen` 中修改，文件包含中英文注释。

主题下拉项使用类似 `28TN-320240H-overlay2` 的名称。切换主题后重启服务或等待配置热加载，并检查日志。

二维码规则：

- `qr_enable=0` 时显示固定管理地址 `http://192.168.22.1`，不是空二维码。
- `qr_enable=1` 且 SSID 不为空时显示 `WIFI:T:WPA;S:<SSID>;P:<密码>;;`。
- SSID 和密码中的分号、逗号、冒号、反斜杠和双引号必须经过 `render.qr_field` 转义。
- 内容不变时不重绘；日志中 `qr updated` 只应出现在内容改变或服务重启时。
- 真实热点不可用时，只能验收 payload 格式，不能把扫码联网标记为通过。

修改二维码通用设置示例：

```sh
uci set displaydash.main.qr_enable='1'
uci set displaydash.main.qr_ssid='DisplayDash-Lab'
uci set displaydash.main.qr_password='<WiFi密码>'
uci commit displaydash
```

## 7. 测试订阅与订阅页验收

演练不得使用真实订阅令牌。可在隔离网络提供两个固定测试 URL，覆盖正常响应、流量统计、到期日、切换和错误响应。HomeProxy 的 URL 使用列表保存；DisplayDash 每个 `config sub` 段独立保存自己的刷新、重置、名称和手动参数：

```sh
uci add_list homeproxy.subscription.subscription_url='http://测试服务器/alpha#Lab Alpha'
uci add_list homeproxy.subscription.subscription_url='http://测试服务器/bravo#Lab Bravo'
uci commit homeproxy
```

在 LuCI 中确认四个页面：总览、主题、设置、订阅。订阅页切换下拉项后，分别保存并重新读取每条订阅的参数；不能把一条订阅的 UA、刷新周期或重置方式覆盖到另一条。

服务端返回 `Subscription-Userinfo` 时，检查 `/tmp/displaydash/proxy.json` 中的 `sub_title`、`sub_used_gb`、`sub_total_gb`、`sub_expire`、`sub_reset_days` 和 `sub_refresh`。

无重置日期时使用项目约定的每月第一天推算方式；屏幕重置字段显示“到期月日 剩余天数”。异常 URL 应保留旧数据显示并标记刷新失败，而不是清空所有订阅信息。

## 8. 恢复配置并验收

在新物理机源码安装完成后恢复备份：

```sh
tar -xzf /tmp/displaydash-backup.tgz -C /tmp
cp -a /tmp/displaydash-backup/displaydash /etc/config/
cp -a /tmp/displaydash-backup/displaydash-screen /etc/config/
cp -a /tmp/displaydash-backup/homeproxy /etc/config/ 2>/dev/null || true
```

恢复后必须按新物理机修正串口设备名、LAN/WAN 接口、管理地址和二维码默认地址，再执行：

```sh
/etc/init.d/displaydash enable
/etc/init.d/displaydash restart
```

验收清单：

- 设备重启后 DisplayDash 自动启动，串口屏持续更新。
- 总览、主题、设置、订阅四个 LuCI 页面可访问。
- 主题通用设置恢复正确，屏幕方向、亮度和页面正常。
- 106×106 二维码显示正确；关闭 WiFi 模式时显示管理地址，内容不变时不周期重绘。
- 两条测试订阅可独立切换、刷新和显示流量/到期信息。
- 备份恢复前后的 UCI 配置、`proxy.json` 和实体屏画面一致。
- 真实 AP、真实代理出口和原路由器恢复不列为已验证项目。

## 9. 故障排查

- `open screen failed`：检查串口设备名、CH340 驱动、权限和是否被 sGUI/串口桥占用。
- 页面仍是旧版本：确认源码已复制到正确目录，重启 `uhttpd`/`rpcd`，并清理浏览器缓存后重新登录。
- 二维码一直显示：确认 `qr_enable` 的 UCI 值和服务日志；关闭时应发送管理地址 payload。
- 二维码每 10 秒闪动：检查日志中是否反复出现 `qr updated`；确认代码只在 payload 改变时调用 QBAR。
- WiFi 扫码失败：先读取实际 payload，检查 `WIFI:` 字段及特殊字符转义，再确认热点安全类型和密码。
- 订阅数据为空：确认 HomeProxy 的 `subscription_url` 列表、当前节点 `grouphash`、URL 可达性和响应头；不要先删除旧的 `proxy.json`。
- 防火墙阻断远程串口桥：只放行指定 Tailscale/LAN 来源和 TCP 2000，完成下载后关闭桥。

## 10. 收尾

完成迁移和验收后停止临时串口桥，确认 COM4 或物理机 `/dev/ttyUSB0` 已释放，保留备份、日志和校验记录。
